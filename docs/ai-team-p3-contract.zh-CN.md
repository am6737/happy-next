# AI Team P3 服务端契约

更新：2026-10-07。此文件由 server 独占维护，CLI/App/wire 只读，root 在明确构建窗口同步共享类型。P3 尚未生产验收；已落地状态见服务端结果报告。

## 独立用户在场凭据与 drain 确认（本轮）

- Server 依赖 `@simplewebauthn/server@14.0.3`；Server `package.json` 已登记，root `yarn.lock` 由 root 在隔离构建窗口同步。生产必须设置 `AI_WEBAUTHN_RP_ID`、`AI_WEBAUTHN_ORIGIN`（精确单一 origin，HTTPS 且 hostname 为 RP ID 或其子域）及独立运营审批公钥 `AI_WEBAUTHN_TRUST_PUBLIC_KEY_SPKI`（Ed25519 DER SPKI 的 base64）；缺项对应入口 fail closed。只有显式配置的 localhost/127.0.0.1 可使用 HTTP 测试 origin。客户端传入的 origin/RP 不参与服务端配置。
- 账号 JWT 调 `POST /v1/ai-team/human-credentials/registration/options` 得 `{challengeId,options}`；平台认证器用 `options` 创建凭据，再调 `POST /registration/verify`，body `{challengeId,response}`。服务端要求 WebAuthn RP/origin、UP 与 UV，challenge 仅两分钟、一次消费；返回 `{credentialId,status:"pending"}`。`GET /v1/ai-team/human-credentials` 仅列该账号凭据状态与创建/信任/撤销/最后使用时间，不返回公钥、credential 原值或私钥。JWT 注册仅证明设备用户在场，不证明旧账号持有人；pending 不能用于恢复。
- 初始信任提升需独立运营线下核对账号及设备归属，然后对规范 JSON `{accountId,credentialId,approvalNonce,actorLabel,evidenceHash,expiresAt}` 签 Ed25519；有效期最多五分钟。账号 JWT 向 `POST /v1/ai-team/human-credentials/:id/trust` 提交 `{approval,signature}`；Server 核验独立运营公钥、账号/凭据、一次性 nonce、DB 时钟期限，并将 `pending` 原子提升 `trusted`，写不可变审计。同一 JWT/账号 seed 无法自行签信任批准。独立运营如何实际核验真人与保管签名密钥仍属部署流程，不能从此 API 自动推断。`POST /:id/revoke` 撤销该账号凭据，同时撤销现有 drain 能力及未完成确认；已撤销凭据不能再确认或领取。
- 原恢复申请仍用原标准过期 capability、machine、dispatch 与最新 attempt proof；`POST /v1/ai-team/capability-recoveries/:id/confirmation/options` body `{generation}` 返回 `{challengeId,options,recoveryId,generation,action:"drain_failed_execution"}`。App 调平台 WebAuthn 后向 `POST /:id/confirm` 发送严格 body `{confirmation:"drain_failed_execution",generation,challengeId,assertion}`。Server 将 challenge hash 与账号、recoveryId、本代 generation、动作、两分钟期限绑定；验证 UP/UV、RP/origin、credential counter，和恢复请求/Workspace revision/latest attempt 在同一事务中复核并消费 challenge。八并发只有一次成功；旧 nonce、旧 generation、过期、跨账号、错 origin/RP、撤权均 409。旧仅 JWT 的 `{confirmation,generation}` 请求为 400，既有旧 confirmed/drain 由迁移 `20261007430000_ai_webauthn_legacy_recovery_fence` 撤销或重置到下一代 pending；领取另要求本代 `human_verified` 审计及当下仍受信的原凭据。
- CLI 只读取确认后的 recovery 状态并以原过期 proof 领取最小 `finish|event|usage` drain；普通 expired renew 仍拒绝。此合同不向 CLI 下发认证器凭据，不允许完成成功、重放工具或审批。App 尚未接平台浏览器/设备注册与确认 UI；旧 App 确认请求会 fail closed。Server 测试使用虚拟 ES256 authenticator 与 fixture 运营密钥，只证明 HTTP/密码学/DB 边界，不是真人或真实设备验收。旧自然 60s/10m/15m expiry 证据来自旧 JWT 确认合同，不能算本新合同完整 E2E。
- `GET /capability-recoveries/:id/audit` 把 `human_verified:<credential hash 前缀>` 只投影为 `human_verified`，不回传 credential 原值、hash 前缀、token 或 challenge。后台 worker 每分钟最多删除 500 条过期超过 24 小时的 challenge；恢复/信任审计不随 challenge 清除。旧账号与真实运营流程仍须单独验收。

## 安全失败与模板审查投影（本轮）

- `GET /v1/ai-team/state` 的 `executions[]` 增加 `errorCode:string|null`，其 `id` 仍是稳定 Task 控制 ID，`orchestratorExecutionId` 是最新实际 attempt。存在最新 execution 时 `errorCode` **仅**取该 execution 的持久字段，即使为 null 也不回退旧 Task；无 execution 才取 Task。`GET /v1/ai-team/workspaces/:id/work-items` 的每项及 `/:workItemId` 详情也增加同样来源的 `errorCode`，保留 `orchestratorExecutionId` 和 `latestExecutionStatus`。`GET /v1/ai-team/decisions` 的每项增加本 Decision 持久 `errorCode`，不从当前 task 猜。三处只投影匹配 `^[A-Z][A-Z0-9_]{0,63}$` 的短代码，否则为 null；不投影 errorMessage、stderr、路径或 token。Workspace 成员必须具当前 Agent+Project 双 canView 才可读 WorkItem；Decision 成员须双 canApprove，撤权后隐藏。owner/admin 沿已有角色授权。
- scoped WorkItem `availableActions` 对 `APPROVAL_SESSION_INTERRUPTED` 与 `APPROVAL_OUTCOME_UNCERTAIN` 不包含 `retry`；`PROVIDER_TEMPORARY_UNAVAILABLE` 等普通失败仍按当前 `canRun` 提供 retry。写端对两安全码的 retry/send-message 409 门禁不变，前端不能仅凭按钮动作推断安全性。App 可按 errorCode 显示精确安全终态、保留普通失败重试；旧无代码状态应保持审慎说明。
- Decision GET 在取得候选行后另起事务，按固定顺序对候选 Workspace 加共享锁，再读取**当前** membership/role 与 Agent+Project 双 `canApprove` grant，在锁持有期间构造响应。管理员撤成员/改 grant/角色变更使用 Workspace 排他锁；已提交的撤权会先于响应复核生效，若复核先拿锁则本次可读先于撤权线性化。撤权后不删除 Decision 审计；无可见项不回传旧候选游标。Decision respond 写事务仍锁 Workspace，成员项目任务也要求双 grant；不能凭 Agent 或 Project 任意一个授权逐操作审批。
- 本人 `GET /v1/ai-team/agent-templates/:id/proposals` 每项与新增 `GET /:id/proposals/:proposalId` 详情返回 `frozenVersion:number|null,frozenContentHash:string|null,frozenContent:受限模板内容|null`。仅当 `sourceExecutionId` 指向同账号 execution、该 execution 持久 `templateVersionId` 属于此模板且已发布、source Agent 与该执行一致、内容 hash 重算正确时返回冻结来源。用户提议和历史缺来源返回三项 null；`expectedCurrentVersion` 是提交时的当前发布版，不代表派发冻结版，版本回滚后可能高于当前版。仅模板账号本人可读列表/详情，跨账号 404；不提供机器 capability、dispatchToken、路径、Agent settings 或运行权限。App 可用受限全文做人工审查，不能把提议自动发布。

## 本轮接口增量

- **CLI 可立即消费的模板提议 context**：`POST /v1/ai-team/executions/:executionId/template-proposals/context`，body 严格为 `{machineId:string,dispatchToken:string,capability:64位小写hex}`，与提议 POST 使用同一个派发下发的 `template_propose` execution capability。成功 `200`：`{templateId,sourceAgentId,sourceExecutionId,frozenVersion,frozenContentHash,frozenContent,currentVersion,currentContentHash,currentContent}`。两份 `Content` 都仅含 `role,description,emoji,skills,responsibilities,instructions`；不含 Agent settings、runtime、目录、权限、token 或其他模板列表。`frozenVersion/Hash/Content` 是**本 execution 派发时 Agent 所绑定的不可变模板版本**；`currentVersion/Hash/Content` 是本次读时模板已发布的当前版本，可能比冻结版本新。Server 在事务里核对两版已发布、内容符合共享 `AiAgentTemplateContentSchema` 且重算 SHA256 与存储 hash 相同，响应再按共享 `AiExecutionTemplateContextSchema` 验证。CLI 可在 `dispatching`、尚未获得真实 provider PID 前读取此只读 context；`POST /executions/:id/template-proposals` 仍必须等到同一 execution 为 `running`，不得提前写入。两端共用同账号、machine、dispatch、有效未撤销 capability、最新 attempt、同账号 Agent 仍绑定冻结版本及当前模板锁的核验。CLI 只能把返回的 `templateId` 用于提议 POST，并把所读 `currentVersion` 用作 `expectedCurrentVersion`；提交仍需处理并发发布导致的 `409 AGENT_TEMPLATE_VERSION_CHANGED`，不得让模型任选 templateId。缺模板/v0/drain/错机/跨账号/旧 attempt/过期撤权/换绑定均 `409 TEMPLATE_PROPOSAL_SCOPE_INVALID`；只读 context 不创建提议、不授予 publish/review/admin。Server HTTP/DB fixture 已覆盖 dispatching 读取200、同期提议409且零写入、running 提议及身份/能力负例；CLI 真实 provider/tool 消费另验。

- 审批会话不可恢复终态：`POST /v1/orchestrator/executions/:id/finish` 的 `status:"failed",errorCode:"APPROVAL_SESSION_INTERRUPTED"|"APPROVAL_OUTCOME_UNCERTAIN"` 在原 finish 事务内将 task/run 置 `failed`、`nextAttemptAt:null`，即使 `retryMaxAttempts` 尚有余量也不自动产生新 attempt。两码含义分别为暂停会话丢失和工具执行结果不确定；均**不是** `rejected`、`completed` 或可自动恢复。该 execution 尚未决定的 Decision 改 `status:"expired"` 并增加版本；所有未送达 Decision 改 `deliveryStatus:"blocked",errorCode:<该失败码>`、清领取 owner/lease。已批准者保留 `decision/decidedBy/decidedAt/operationId/actionHash`，已送达者保留 delivered 历史。原 token 同一 finish 重放仍 200、错 token 409；普通 `PROVIDER_TEMPORARY_UNAVAILABLE` 按已有 retry 策略排队。App 应显示“执行中断，审批结果未确认，需要人工检查”，不可展示“已拒绝”或“已交付”；Inbox 可按 `expired` 与 `blocked` 显示历史，不提供原请求的批准/投递重试。
- 对上述两码，`POST /v1/ai-team/work-items/:id/retry`、原聊天目标恢复和旧 `POST /v1/orchestrator/tasks/:taskId/send-message` 均返回 409，不从原 worktree/session 创建新 attempt。需人工核对外部副作用后以**新任务**明确发起，不能把一键 retry 当安全恢复；普通失败仍保留显式重试。真实 Codex app-server 的暂停/工具 journal/进程组故障行为由 CLI 验收，Server 的 finish/Decision 状态验收使用真实 PostgreSQL/HTTP fixture；手动入口另用真实 JWT/machine-scoped Socket fixture 验证，不把受控 Socket 称为 daemon SIGKILL E2E。
- Agent 受信模板提议：迁移 `20261007410000_ai_execution_template_proposal_scope` 在 `OrchestratorExecution.templateVersionId` 冻结派发时的 Agent 模板绑定，在提议记录增加 `sourceExecutionId`。仅 AI WorkItem 且已绑定模板的 v1 派发能力得到 `template_propose`；旧 v0/人工补领与 drain 不新增该 op。`POST /v1/ai-team/executions/:executionId/template-proposals` 请求 `{machineId,dispatchToken,capability,templateId,clientRequestId,expectedCurrentVersion,content,note}`；事务核验账号/当前 machine/dispatch、有效且未撤销的 `template_propose` capability、running/latest attempt、当前 Agent 绑定与冻结模板版本。提议的 `sourceAgentId/sourceExecutionId` 由 Server 派生，不采信请求字段；仅创建 pending 提议，人工 `/review` 才能发布。相同请求 200，错 scope/旧 attempt/错模板 409。CLI 尚未消费此新 API，测试机器/HTTP 认证为 fixture；不得宣称 Agent 已在真实 daemon 上报经验。

- Agent 模板经验提议：`POST /v1/ai-team/agent-templates/:id/proposals` 请求 `{clientRequestId,sourceAgentId?,expectedCurrentVersion,content,note}`，仅账号本人可提交；`content` 只接受模板的角色/描述/图标/技能/职责/指令，不含 runtime、路径或权限。`clientRequestId` 同内容重放 200，变更内容/来源/版本/说明 409。`GET /:id/proposals?status=pending|accepted|rejected` 仅账号本人读取不可变内容、hash、来源及审查结果。来源 Agent 仅表示同账号用户选择的关联对象，不证明 Agent 自主或受信上报。`POST /:id/proposals/:proposalId/review` 请求 `{decision:"accepted"|"rejected",confirmed:true,expectedCurrentVersion}`；模板行锁与当前版本 CAS 后，接受在同事务创建不可变已发布版本并更新 currentVersion，拒绝只写审查记录；相同审查重放 200，异议或旧版本 409。账号 JWT 仍是现有人工身份，未实现独立真人在场证明。迁移 `20261007390000_ai_agent_template_proposals`。
- 站内订阅通知：评论和元数据变更在原事务内按 WorkItem 订阅人写入幂等记录，操作者本人不收；无正文、路径、token 或外部邮件/Slack。`GET /v1/ai-team/notifications?cursor=&limit=1..100` 返回 `{items:[{id,workItemId,action,actorAccountId,createdAt,readAt}],nextCursor}`；`POST /v1/ai-team/notifications/:id/read` 幂等标已读。每次读取/标记均在 Workspace 行锁下复核当前 membership 与 WorkItem 的 Agent/Project 双 `canView`，撤权后历史记录不可见且不可标记；分页可因过滤撤权记录出现空页但仍有 `nextCursor`。无推送 fanout；客户端轮询。迁移 `20261007400000_ai_work_item_notifications`。

- Redis RPC bridge 使用独立、关闭离线命令队列的短超时连接；路由读取、PUBLISH、ACK 后 owner 校验均受命令超时约束。每个跨实例请求含绝对 `deadlineAt`，接收实例在 Redis owner 读取前后、发机器 Socket 前检查；过期或缺 deadline 的消息不调用机器。发布命令超时可能已进入 TCP 缓冲时，发起实例仍等待同一绝对截止才报告失败，防止 HTTP 已 503 后 Redis 恢复再执行；回复在截止后也不接受。明确桥不可达、路由缺失、owner 变化和 RPC 超时归为 `AI_RPC_BRIDGE_UNAVAILABLE`，未捕获的 HTTP 路由返回固定 `503`、`Retry-After: 2` 且无 Redis 连接细节；后台 worker 继续各自 durable retry。现有根隔离 Redis pause 诊断行为字段均通过，整体 `unknown` 因并行消费者更改候选摘要，须冻结候选后再次取得整轮 exit0。

- 二次断网 drain：同 execution 的恢复请求保留 ID，响应新增单调 `generation`（首轮 1）。原 10 分钟 drain token 到期，或未领取的 15 分钟申请到期后，CLI 仍用**原标准过期 capability**、固定 machine/dispatch/当前 attempt 再调用 `POST /v1/ai-team/executions/:id/capabilities/recovery-requests`。Server 在 Run 锁事务内重核原 proof 的 24 小时窗口、身份、Workspace revision 和前一 drain 到期；请求创建与确认还锁定 capability/Workspace 并在锁后重核撤权，返回新的 `pending` 与 generation。前一 drain 尚有效或被主动撤销时不能自动重开。WebAuthn `/confirm` 每一轮都必须带当前 `generation`、challengeId 和 assertion；`/claim` 第二轮及以后必须带当前 generation，首轮省略仅保留机器领取接口的兼容。旧 generation 的确认/领取返回 409，新轮必须由 owner 再次进行平台用户在场确认 `drain_failed_execution`，不继承上次批准。
- `GET /v1/ai-team/capability-recoveries` 增加 generation；`GET /v1/ai-team/capability-recoveries/:id/audit` 仅所属账号返回各轮 requested/confirmed/claimed 时间与 actor，不含 token/hash/path。迁移 `20261007380000_ai_drain_reconfirmation` 增加 generation、不可变审计记录并回填旧请求首轮审计。普通过期 `/renew` 仍 409；新 drain 仅 `finish|event|usage`，只能 `failed/EXECUTION_CAPABILITY_EXPIRED`，绝不重启模型/工具、放宽 approval 或标记 completed。自然到期正例使用原标准 capability 的实际 60 秒；10m/15m 边界测试只缩短自有 fixture 行的期限，生产默认时长不变。
- `GET /v1/ai-team/agents/archived?limit=1..100&cursor=` 仅当前账号，按归档时间分页返回 `{items:[{id,name,role,archivedAt,enabled}],nextCursor}`。错误或跨账号 cursor 为 400，不返回指令、settings、path 或 token。现有 restore 成功后从列表消失，且仍 disabled。
- 人类 owner 独立确认的 Server 校验和旧账号 fail-closed 迁移已按本文件顶部 WebAuthn 合同落地；App 平台凭据 UI、真实设备/浏览器与线下初始信任核验尚未验收。账号 Ed25519 seed 或 JWT 仍不计作独立人类证明。

## 人类身份与权限

- `AiWorkspace` 是人类协作边界；现有 `Account` 是默认 Workspace 的 owner，旧资源 `accountId` 继续指向 owner account，不改旧运行中 task。`AiWorkspaceMembership(workspaceId,memberAccountId,role)` 的 role 为 owner/admin/member，和 Agent 使用的 `AiTeamMember` 完全分离。所有共享访问先解析 Workspace 与成员，再以 owner account 查询资源；无成员关系为 404。
- 资源可见与动作分开：`view` 查看 Project/Agent/WorkItem/事件；`run` 建单、重试、steering、委派；`approve` 人工决定；`admin` 管成员、权限和预算。默认 owner 全权，admin 除所有权转移外全权，member 仅显式授予的 Project/Agent view/run/approve。旧账号无 Workspace 行时按 owner 惰性映射，不能用请求中的 accountId/TeamMember 授权。
- `GET /v1/ai-team/workspaces` 返回当前人类主体可访问空间；成员变更采用 owner/admin 管理端点并在事务中增加授权 revision。撤权立即使新请求及 capability 失效，正在运行的 execution 按状态机取消或完成受限上报，不隐式转移 ownership。
- `POST /v1/ai-team/workspaces/:workspaceId/projects/:projectId/run` body `clientRequestId,agentId,title,summary`：owner/admin 或同时获 Project 与 Agent `canRun+canView` 的 member 可建 `run_only` WorkItem。请求以 `(owner account,conversation,workspace:actor:clientRequestId)` claim 幂等；Run/WorkItem 仍归 owner account，创建事务提交前锁 Workspace，复核成员/grant、Project active/currentVersion，再固定 Project version/machine/base。相同请求重放返回原 Run，改内容 409，撤权 404/409。成员使用下述 WorkItem 控制 URL；普通会话消息路由和机器 finish 仍属于 owner/受信 execution 身份，不共享 owner token。
- `GET /v1/ai-team/workspaces/:id/grants?memberAccountId=` 仅 owner/admin 可读；在 Workspace 行锁事务中复核 actor 与目标成员，返回 `{memberAccountId,role,authRevision,grants:[{resourceKind,resourceId,canView,canRun,canApprove}]}`。目标成员不存在、角色不足或跨空间均 404；不返回 token/secret。App 编辑 grant 前用此快照回填，`PUT /workspaces/:id/grants` 可带 `expectedAuthRevision`，在同一 Workspace 行锁内 CAS，版本变化返回 `409 AUTH_REVISION_CHANGED`；旧客户端省略该字段时仍按既有单资源更新语义，写后应重新 GET。
- `GET /v1/ai-team/workspaces/:id/work-items?limit=1..100` 与 `GET /v1/ai-team/workspaces/:id/work-items/:workItemId` 为刷新后的成员投影：owner/admin 看本 Workspace owner 资源，member 对 Project WorkItem 必须同时有 Project 与 Agent `canView`，非 Project WorkItem 需 Agent `canView`。返回标题、摘要、priority/labels/dueDate/metadataRevision、归属、Project 版本、Run/task/latest execution 状态、`workspaceAuthRevision`、`orchestratorExecutionId` 及 `availableActions`。动作按当前双 grant 与任务状态投影，可为 `cancel|retry|steering|approve|changes_requested`；mutation 仍在事务里复核，旧 UI 投影不等于永久许可。不返回 prompt、worktreePath、内部执行 token。跨 Workspace/未知 ID 为 404。
- 旧 WorkItem 控制 URL 现在支持人类 Workspace member：`POST /v1/ai-team/work-items/:id/cancel|retry`、`POST /work-items/:id/steering`、`POST /work-items/:id/steering/:steeringId/retry`、`POST /work-items/:id/acceptance`。member 对 WorkItem 的 Agent 及其 Project（若有）均须 `canView+canRun`；验收 `approved` 须 `canView+canApprove`，`changes_requested` 同时须 `canApprove+canRun`。owner/admin 不受资源 grant 限制。每个 mutation 在 Workspace 行锁下重读 membership/grant，撤权与提交线性化；无权/跨账号均 404。Run/Conversation/InboundRequest 继续归 owner account，成员 clientRequestId 加 actor 前缀隔离，持久请求 payload 与用户消息记录 actorAccountId；不使用共享 owner token。`GET /work-items/:id/steering/:steeringId`、`GET /work-items/:id/integration-verification`、`GET /work-items/:id/collaboration` 允许具有对应双资源 `canView` 的成员。
- 新 steering POST body `{clientRequestId,targetTaskId?,text}`，要求当前 Run 恰有一个 running execution；多个执行须显式 targetTaskId，创建 durable AiSteeringMessage 并返回 `202 {workItemId,targetTaskId,steeringId,status:"queued"}`。`AiSteeringMessage.actorAccountId` 为新增 nullable 列，旧行可为空，新增行固定实际人类 actor。相同 actor/clientRequestId/内容重放原结果，改内容 409。旧会话模型 steering 路由仍按 owner 的会话身份使用。
- Agent 生命周期：`PUT /v1/ai-team/agents/:id` 的 `enabled=false` 是暂停新任务，保留历史与当前任务；`DELETE /agents/:id` 是归档，若 Agent 担任活跃 Team leader 或有 queued/running/canceling WorkItem/委派 Task 返回 409，不把运行中的执行变成孤儿。新建单/团队成员变更/委派在归档的同一 Agent 行锁上复核。`POST /agents/:id/restore` 仅账号 owner 使用，清 `archivedAt`、保持 `enabled=false`，同值重试 200 `{duplicate:true}`，外账号 404；再次启用须显式 PUT。App 不应把 enabled 切换称为归档或恢复。

## Execution Capability

### 机器协议探测与人工审批准入

- machine-scoped Socket 仅可登记自身 `${machineId}:orchestrator-features`。Server 建立 `permissionMode=approval` 的新任务前，实时向目标 machine 调用该 RPC，参数为 `{nonce,protocolVersion:1}`；响应必须精确包含 `{nonce,machineId,protocolVersion:1,executionCapabilityVersion:1,approval:{provider:"codex",runner:"app-server",operationDecisionVersion:1}}`。`nonce` 必须原样回显，Server 只信已按账号和 machineId 验证的 Socket 当前 owner/epoch，不信 Agent settings 或客户端自报能力。
- 仅 `engine=codex`、`allowDelegation=false`、无 team 的任务可走该准入；旧机器、RPC 不可达、字段/版本不匹配返回 `AI_APPROVAL_RUNTIME_UNSUPPORTED`，不能静默切换 `guarded_auto`。Server 每次新 execution 派发前仍需复核该协议；新旧 machine owner 切换后的旧 ACK 不能视为成功。
- CLI 后续实现 `${machineId}:orchestrator-features` 时，只在实际 app-server runner、逐操作 Decision 代理和受限 journal 均就绪时发布上述能力；旧 CLI 不注册此方法，继续安全拒绝。
- 派发前再次调用 features；注册该方法的机器必须发布 `executionCapabilityVersion:1`，Server 对新 execution 原子固定 `capabilityProtocolVersion=1` 与最小 `capabilityAllowedOps`，并在 `orchestrator-dispatch` payload 下发 `executionCapability:{token,protocolVersion:1,allowedOps,expiresAt}`。旧未发布 features 的 execution 版本为 0，可按既有 dispatchToken drain；版本 1 的 identity/finish/Skills/delegate 必须带下发 token，同账号客户端不能通过公用 mint 接口给该 execution 补领。机器不支持或响应不完整时派发失败，不降级为版本 0。
- 对持久 `AiWorkItem` 关联的**新派发**，未注册 features v1 的机器直接以 `AI_RUNTIME_PROTOCOL_UNSUPPORTED` 失败，不发送 dispatch RPC；generic `OrchestratorRun` 无 AI WorkItem 的旧任务仍可按版本 0 派发，先前已 running 的版本 0 execution 可按原 dispatchToken 完成。AI WorkItem 的“新”以执行派发时的 DB 关联为准，不信用户 metadata。

- Server 发放一次 execution 绑定能力：随机 256-bit token 只在下发时出现，数据库只存 SHA-256。scope 固定 owner account、workspace/project/version、run/task/execution/machine、allowedOps、expiresAt、authorizationRevision；DB 主动撤销或成员撤权后拒绝。
- `capabilityProtocolVersion=1` 的 identity/finish、Skills download、delegation 必须传 `capability`（64 位小写十六进制），事务内校验固定账号/execution/machine/op/expiry/revision，仍要求 dispatchToken；省略或错误返回 409/403。版本 0 的旧运行不传时沿用原 dispatchToken 路径直至 drain，传入则同样严格校验。事件、usage、decision_request 继续强制 capability。`POST /v1/ai-team/executions/:id/capabilities/renew` body `{machineId,dispatchToken,capability}` 仅在版本 1 当前 active execution、旧 token 有效且含 finish 操作时签发同 scope 的新一小时 token；旧行不删除，撤权/换机/旧 attempt/过期拒绝。CLI 必须在到期前续期并原子保存新 token。
- 过期后恢复是单独三步，普通 renew 继续拒绝过期 token。CLI 用 `POST /v1/ai-team/executions/:id/capabilities/recovery-requests` body `{machineId,dispatchToken,expiredCapability}` 登记；服务端要求原始标准 capability 已自然过期不超过 24 小时、未撤销、Workspace authRevision 不变、原 run/execution 仍 running 且为最新 attempt、三项执行身份已绑定，同请求幂等返回恢复请求 ID。owner 通过 `GET /v1/ai-team/capability-recoveries?status=pending|confirmed&limit=` 查看，再 `POST /v1/ai-team/capability-recoveries/:id/confirm` body `{confirmation:"drain_failed_execution"}` 明确确认，15 分钟内有效。跨账号、错机、旧 attempt、取消、授权变更均 409；列表不含 token/hash/path。
- CLI 重连后 `POST /v1/ai-team/capability-recoveries/:id/claim` body `{executionId,machineId,dispatchToken,expiredCapability}`；Server 先向当前 machine-scoped Socket 的 `orchestrator-features` 发 nonce 并核验 v1，再在 Run 锁事务内复核原 token hash、固定 session/worktree/branch、授权修订、最新 attempt 与确认。最终 token 使用 PostgreSQL `INSERT ... SELECT` 在实际签发时复核申请截止、确认状态、原 token/Workspace revision、当前 run/execution/machine/dispatch 和最新 attempt；等待中的早期读取不能越过截止。返回一次短期 `recoveryMode:"drain"` token，10 分钟、仅 `finish|event|usage`；重复 claim 撤销前一 drain token 并发新 token。此能力不能 identity/Skills/delegate/decision_request，也不能 renew。`finish` 仅接受 `status:"failed",errorCode:"EXECUTION_CAPABILITY_EXPIRED"`，无 finalResponse/commit/PR/integrationProof、无 exitCode 0，且不自动重试；同 token 的已落库失败重放返回 200。未知工具 invoking 仍须 CLI journal 保持不确定并停止工具，不得借 drain 回报 completed。当前 JWT 是账号级，owner 确认 API 尚不能密码学区分持有同一账号凭据的 daemon 与人类；App 须呈现明确确认，生产级人类二次认证仍待实现。
- `POST /v1/orchestrator/executions/:id/identity` body 为 `dispatchToken,machineId,childSessionId,worktreePath,branchName`。仅同账号当前 running Run、最新 running execution、正确 token/machine 可首次绑定；Project task 同时复核冻结版本/machine/base/hash。三字段完整后不可变，同值重放 200、异值/旧 attempt 409，跨账号 404。CLI 必须在运行中首次逐操作 Decision 请求前调用，不能等 finish 才报告 session/worktree/branch。已绑定 execution 的 finish 必须带相同三字段，旧未绑定运行维持兼容。

## 事件与用量

- `executionEvent`：`eventId,executionId,seq,kind,phase,occurredAt,redactedSummary,artifactRef?,schemaVersion`。Server 对 `(executionId,eventId)` 幂等、`seq` 单调，限制字节并再脱敏；GET 按游标分页，跨账号/非成员 404。原始工具载荷不作为共享审计，过期内容删除与审计元数据留存分开。
- `usageDelta`：`executionId,provider,model,sourceEventId,inputTokens,outputTokens,costMicros?,pricingVersion?,measuredAt`。按 `(executionId,sourceEventId)` 幂等；未知价格必须标 `unknown`，不得伪装 0。预算 policy/reservation 绑定 Workspace/Project、周期、revision，Run 准入事务锁定 used+reserved；终态消费或释放。自动 settled 后的新已知费用在接受事务内按该 sourceEventId 一次性增加 reservation.actualMicros 与 policy.usedMicros，迟到顺序不影响合计；自动 settled 后未知费用及人工最终结算后的新费用返回 409，不能接受后静默漏账。人工 resolve 的 `actualMicros` 是管理员声明的该 Run 最终总额，并非可与迟到 delta 自动相加的补差。Prometheus 只用低基数状态 label，不放 account/prompt/run ID。

## 待决策与恢复

- `DecisionRequest` 固定 WorkItem/Run/task/execution、kind、eligibleRole、status/version/expiry 与审查 payload 摘要。两个审核人以 `decisionId+version+clientRequestId` CAS，只有一次生效；批准/拒绝后通过 durable outbox 恢复或终止原 execution，不能新建未关联任务。Feed 只投影待决策，不以已读/归档执行审批。
- App 展示 pending/history；CLI 恢复时校验原 execution、machine、worktree 与已生效决定。所有动作先过 Workspace membership 和 capability；跨空间 ID 猜测按 404 返回。
- scoped Workspace WorkItem 列表/详情增加 `orchestratorTaskId`（稳定控制 ID）与 `orchestratorExecutionId`（该 Task 最新实际 attempt，可能为 null）；不返回私有 worktree 路径或 dispatchToken。人工验收 `POST /v1/ai-team/work-items/:id/acceptance` 的 approved body 支持 `reviewedExecutionId`，必须等于用户实际看到的 execution 且与锁内最新 execution 相同。旧客户端缺字段仅首个 attempt 可批准；返修后的任何 attempt 缺字段 409。App 应始终传该字段，不能根据当前最新 completed 自动代替用户审看的版本。
- 当前 Server API：`POST /v1/ai-team/executions/:id/decisions` 由绑定 execution 的 `decision_request` capability 创建。旧请求 body 为 `machineId,capability,kind:approval|review,summary,expiresAt`，仅保持 legacy 兼容，不能作为逐操作执行授权。新逐操作请求额外同时提供 `operationId`（同 execution 内唯一，1..128 字符）、`actionType`（小写规范动作类型）、`actionHash`（规范化动作及参数的 SHA-256 小写十六进制），`kind=approval`；缺一项即 400。`summary` 仅供人阅读，不用于执行授权。同一 operationId 重放的 kind/type/hash/summary/expiry 必须完全相同，否则 409；不同 operationId 可各自待批，批准一个不会批准其他操作。迁移 `20261007310000_ai_decision_operation_identity` 将唯一键改为 `(executionId,operationId)`，另有 legacy `(executionId,kind) WHERE operationId IS NULL` 唯一索引。
- Server 从当前 execution DB 行读取 `childSessionId,worktreePath,branchName`；逐操作请求缺这些受信身份会被拒绝。DB 仅保存 worktreePath SHA-256，决策在 respond、retry 和 outbox 发 RPC 前均核验固定 run/task/execution/machine/dispatchToken/session/worktree hash/branch。`GET /v1/ai-team/decisions?status=&cursor=&limit=` 返回授权 Inbox，包括 `operationId,actionType,actionHash`；`POST /v1/ai-team/decisions/:id/respond` 携带 `version,clientRequestId,decision:approved|rejected,note`，在事务里锁行并按人类成员/grant CAS。CLI 只可释放匹配 operationId+actionHash 的单次暂停动作，不能切换整任务 `guarded_auto`。
- `POST /v1/ai-team/decisions/:id/retry` 仅 owner/admin 可把 blocked 的已决定投递重新排队；在 Workspace、决定与 execution 行锁内复核原 attempt/machine/token 仍为 running，并用实际数据库时钟拒绝到期许可。有效 pending 重试幂等返回 200，到期/终态/身份变化 409，跨空间 404。缺 CLI RPC 时继续 pending。
- 下游 CLI 的 `${machineId}:orchestrator-decision` 受限 RPC 接收 `decisionId,executionId,dispatchToken,version,decision,note,operationId,actionType,actionHash,childSessionId,worktreePathHash,branchName,expiresAt`。`expiresAt` 为服务端固定的 ISO 时间；CLI 在真正释放动作前以当前时钟再次拒绝过期许可。逐操作请求必须核验当前暂停的同一 execution 与动作 hash，在本地 journal 持久去重后才返回 `accepted:true`；legacy 的空 operationId 不得授权具体动作。Server 在 Workspace 行锁下复核当前审批人、决定到期和 execution 身份，并保持锁至 RPC 应答与投递状态写入；撤权与投递按提交顺序线性化。派发前与 ACK 时再用数据库实际时钟检查 claim lease、owner 和 version；失租只回 pending，不记 delivered。ACK 失租窗口可能已发 RPC，CLI 必须按 decisionId+version 在本地幂等。无 RPC、拒绝或超时保留 durable pending 并重试，身份变化标 blocked，到期标 `decision_expired`。当前 server 真实 RPC 仅由 fixture 证明 payload 与 outbox；实际 CLI 暂停/恢复尚须跨包验收，不能称完整人工审批产品。

## 验收边界

### 跨实例 Socket 路由

- 每个 API 实例通过 Redis 的 `happy:rpc:route:v1:*` 记录 `(accountId,method,instanceId,socketId,epoch)`，30 秒租约、10 秒续租；机器方法只允许已按账号和 machineId 核验的 machine-scoped Socket 登记。登记 epoch 单调递增，注销只能删自身 epoch。所有远端请求由当前 owner 实例转到实际 Socket，发起方及 owner 在 ACK 前后复核 Redis 当前 owner；过期或换主 ACK 不能当作派发成功。执行副作用仍须用 executionId/dispatchToken 在 CLI 持久幂等，因为网络 ACK 丢失不能证明机器没有执行。
- Redis Pub/Sub 转发账号范围的 `update/ephemeral`，各实例仅向本机同账号连接投递，保留 recipientFilter；发起实例不重复回送自己发布的事件。持久 update 的断线补发继续以用户 seq/数据库为准，Pub/Sub 仅是在线通知。Redis 不可用时跨实例 RPC 失败关闭，不能用本机不存在的路由宣称成功。
- 终态通知的离线 feed 回退读取 Redis 中按 `(accountId,sessionId)` 隔离的 session-scoped Socket 在线租期；连接每 10 秒续租、30 秒过期，断线按 socket 成员移除。事件本身仍经 Pub/Sub 投递。在线记录只用于避免跨实例误建重复 feed，不是授权依据，也不承诺远端客户端已收到事件；崩溃后的失效窗口最长 30 秒。
- 会话消息的 CLI 回执判断另记录 `supportsMessageReceipt` 在线租期。B 向 A 上的 CLI 发消息时，B 可将 delivery issue 置为 waiting 并等待真实回执，不能因 B 本机无 session Socket 立即写 `no_cli_connection`；跨实例在线记录过期或 Redis 不可达时仍按离线处理，后续同步以持久消息为准。
- App/session Socket 的 `rpc-call` 也使用同一跨实例 owner：本机连接先检查当前 owner/epoch，远端调用经 Redis 转发。共享 session 方法先执行既有访问等级和方法白名单，再按会话 owner 账号查路由；不允许借共享会话调用 owner 的任意机器 RPC。owner 换主前已发请求的旧 ACK 拒绝，发请求前发现旧本地路由则转发到新 owner。
- Server 包独立 fixture `scripts/ai-team-cross-instance-real.mts` 使用两个进程/43115 与 43117、真实 JWT/PostgreSQL/Redis/Socket.IO，验证 B 调 A 的机器 RPC、B 事件到 A 用户 Socket、跨账号事件/RPC 隔离、B 实际 `executeSchedulerActions` 从 DB 自有 AiWorkItem 派发到 A 并核对 DB token hash、B 抢占机器 owner 后旧 A ACK 被拒、A 调 B、A `SIGKILL` 后旧路由租约过期。机器 RPC 回执为受控 Socket fixture；尚未运行实际 daemon/provider，也未证明 public submit/model/cancel 的完整跨实例工作流。
- 该 fixture 现另走 B 上真实 `requestStructuredModel` 与 `executeSchedulerActions(cancel)`，A 上受控 machine Socket 回执；模型结构解析成功、其他账号请求被拒、取消 RPC 恰好一次。还验证 B 实际 `dispatchSessionMessage` 写 DB、A 的 session Socket 接收持久 update 且 delivery issue 保持 waiting。上述均不等同于公开 submit、真实 daemon/provider 运行或取消真实进程。

至少覆盖旧账号 owner 自动映射、两人角色矩阵、跨 workspace/Project 猜测、成员撤权后旧 capability、错 machine/旧 execution/op；事件断线重复及分页、脱敏/retention；预算双 worker 同时准入、usage 重复/乱序与未知价格；审批并发只一人成功、过期/撤权不唤醒。真实 PostgreSQL/HTTP 与临时 CLI fixture 区分记录，外部 GitHub 404 不阻塞本地验收。

## 当前服务端实现范围

- 已有 `GET /v1/ai-team/workspaces`、`GET /workspaces/:id/members`、`PUT/DELETE /workspaces/:id/members/:accountId`、`PUT/GET /workspaces/:id/grants`、`GET /workspaces/:id/resources?kind=project|agent`，以及 Workspace Project run/WorkItem list/detail、上述 scoped WorkItem 控制/验收。owner 惰性创建默认 Workspace；member WorkItem 列表/详情按 Agent+Project 双 canView，mutation 按双 grant 并锁 Workspace。普通会话聊天、CLI 机器 finish、项目/Agent 管理仍用各自既有身份，不把成员 grant 当作机器执行凭据。
- `POST /v1/ai-team/executions/:id/capabilities` 是版本 0 的迁移期接口，只能领取 `event|usage|decision_request`，不能给版本 1 execution 补领，也不能公开 mint finish/Skills/delegate。撤销成员时旧 capability 保留 revoked 记录；owner 可在旧版本 execution 活跃期间以当前 Workspace revision 再领取受限遥测能力，不能恢复已撤销 token。版本 1 的初始 token 仅由 Server 派发创建，DB 只存 SHA-256；新 token 经上述受限续期接口产生。CLI 工作树已有 features v1/派发能力消费源码，实际 provider/daemon/续期跨包闭环仍待验收。
- 事件：`POST/GET /v1/ai-team/executions/:id/events`；写入需 event capability，按 eventId 和 seq 唯一，重复同内容返回 200，冲突 409，服务端二次脱敏。URL 先用标准解析器识别 userinfo 与解码后敏感 query key（包括签名与百分号编码 token），整体替换凭据 URL；再执行 token、环境变量、私有路径规则。GET owner 或具有对应 Project/Agent `canView` grant 的成员可按 afterSeq/limit 分页；外账号 404。30 天 worker 仅清 redactedSummary 并保留事件元数据。CLI 事件源已在其报告中实装，跨包长期脱敏语料仍需扩展。
- 预算：`PUT /v1/ai-team/workspaces/:id/budget`、`GET /workspaces/:id/budgets`，AI `submitWork` 和普通 `/v1/orchestrator/submit` 均在创建 Run 的事务内预留 perRunReserveMicros，后者超限返回 `AI_BUDGET_EXCEEDED`/429；策略未配置时旧路径不变。PUT 在 Workspace 行锁后复核 admin 身份。`POST /v1/ai-team/executions/:id/usage-deltas` 需 usage capability，sourceEventId 幂等，已签发且未撤销的 usage capability 可在 execution 终态后有效期内上报迟到计量；已自动结算后的新已知费用同步补账。未知成本保留 reservation/unknown，绝不记为零；人工最终金额通过下述 resolve API 声明。跨包 runtime 的真实 provider 成本仍不确定，不能把 token 数量冒充报价。
- `AiDecisionRequest`、上述 API、审批 CAS 与 durable outbox 已落地，迁移 `20261007290000_ai_decision_request` 与新增逐操作身份迁移 `20261007310000_ai_decision_operation_identity`。CLI 审批专用 RPC/执行暂停与恢复仍在跨包集成，不能宣称原 execution 已实际恢复。当前请求只允许运行中的 AI WorkItem execution，成员可批准需对应 project 或 assignee agent 的 `canApprove` grant。
- `canRun`/`canApprove` grant 必须同时 `canView`，否则写入 400。审批 outbox 在领取后复核审批人的当前 membership/grant；撤权或固定 execution/token 变化会 blocked。仍需 CLI 决定恢复协议以及撤权与外部 RPC 同时发生时的进一步端到端 fencing。
- `ai_workflow_queue_items{queue,status}` 由现有 60 秒数据库指标 worker 更新，标签仅限固定队列/状态：pending 决策、pending/blocked 投递、reserved/unknown 预算。`ai_budget_max_utilization_ratio` 无标签，`ai_budget_policies_high_water{threshold="0.9"}` 仅固定阈值标签；两者用当前 active、在有效 period、limit>0 策略的 `(used+reserved)/limit` 计算，不导出账号、成员、run、Project 或路径。Prometheus 规则已在 root 独占文件验证，Server 实际指标与告警完整端到端仍未通过容量验收。
- DB 容量：Server 每实例 Prisma 默认 `connection_limit=10,pool_timeout=5s`，已有 URL 显式参数优先；`AI_DB_POOL_MAX` 可在 1..50 内配置缺省连接上限，部署须按 `副本数×每副本上限+后台/迁移/管理保留` 小于 PostgreSQL 可用连接预算。AI 事件 GET 每实例默认最多 64 个并发读取，`AI_DB_READ_CONCURRENCY` 可在 1..256 调整；超额准入或识别到 Prisma P2024/P2037/PG53300、明确连接耗尽文字时返回无秘密 `503 {errorCode:"AI_DB_CAPACITY"}` 与 `Retry-After: 2`。其他异常保留 500，不伪装超载。固定 `ai_db_capacity_rejections_total{reason="admission|pool"}` 与 `ai_db_active_reads` 无账号标签。当前入口级并发门只覆盖事件 GET，全局错误处理覆盖其他路由的已识别数据库耗尽；尚未实现全服务共享查询并发预算。健康 32 并发全 200、role CONNECTION LIMIT2 加两条实际 pg_sleep 后 8 请求全 503、释放后完整分页恢复已在隔离库验证；完整容量/告警候选门禁仍未通过。
- 未知成本人工恢复：`POST /v1/ai-team/budget-reservations/:id/resolve`，body 为 `clientRequestId,actualMicros,note`，仅 Workspace owner/admin 可调用。服务端锁 Workspace 与 policy，确认 Run 终态且 reservation 为 unknown 后一次性从 reserved 转入 used，并记录操作者、请求 ID、说明；同请求同金额同说明重试 200，换金额/说明或已结算返回 409，跨账号 404。迁移 `20261007300000_ai_budget_manual_resolution`。此为人工核对后的成本声明，不代表 provider 报价证据或自动计价。
