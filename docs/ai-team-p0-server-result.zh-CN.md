## Server watchdog 兜底期限修复（2026-10-08）

- `sources/app/orchestrator/scheduler.ts` 将 running execution 的 Server 兜底终态改为 `startedAt + timeoutMs + 60_000ms`。派发给 daemon 的 `timeoutMs` 不变；CLI watchdog 仍在原期限发 SIGTERM、5 秒后 SIGKILL，随后等进程组退出、持久化事件/usage/finish，并以 15 秒间隔重试未送达 finish。60 秒是固定上限，覆盖进程退出及常规 finish 上报窗口；到期仍未收到报告才记 `TASK_TIMEOUT`。没有无限延长任务执行或改用户可设置的 timeout。

## 实施

- `AiInboundRequest` 以 `(accountId, conversationId, clientMessageId)` 唯一 claim，记录请求 hash、owner、lease 和持久响应；并发、冲突、响应丢失重试分别返回唯一 owner、409、原响应。消息、run、task、WorkItem 和完成标记在同一事务内写入。`AiMessage` 另有消息 ID 唯一约束。

- 直接 GitHub assignment 用账号 OAuth 核验仓库写权限及 Issue 身份，记录仓库 ID grant。Webhook 先验 HMAC，再按 delivery hash/owner/lease 去重；DB 回写和成功标记同一事务。账号、仓库 ID/名称、installation、PR 编号/URL、任务 branch/commit 与 closing Issue 均限制关联；新 PR 的 NULL 初始状态已修复，旧事件不回退 merged。
- 新工作项不继承上一任务 child session。显式 resume 核验原机器、仓库及 branch/base 身份。headless `approval` 和 Gemini 只读不安全组合在建单前拒绝。

- 聊天与 WorkItem 完成消息只消费 finish 中独立的 `finalResponse`，不从 `outputText/outputSummary/stderr/diagnostics` 派生。无 finalResponse 的成功 exit 0 不产生 agent 聊天消息。日志仍保存在执行记录；GitHub marker 仅从 finalResponse 取候选，再通过独立 API 核验。
